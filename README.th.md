# bladeball-ledger

ระบบจดรายรับรายจ่ายของร้านขายไอเทม **Blade Ball (Roblox)** ที่ผมทำขายจริงมา 2 ปี
เก็บข้อมูล → คำนวณต้นทุนจริง → วิเคราะห์ด้วย SQL → เอาไปตัดสินใจจริง

> **Status:** เริ่มเก็บข้อมูล 15 ก.ย. 2026 · ก่อนหน้านี้ทำมา 2 ปีโดยไม่เคยจดเลย
> **ถึงตอนนี้ (15 ก.ย. – 17 พ.ย. 2026):** 456 ออเดอร์ · 612 ชิ้น · ยอดขาย 130,486 บาท · ซื้อของเข้า 133 ครั้ง

---

## โจทย์

ร้านนี้ขายไอเทมเกมให้คนไทยผ่านกลุ่ม Facebook 2 กลุ่ม
ก่อนมีโปรเจกต์นี้**ไม่มีข้อมูลอะไรเลย** ทุกตัวเลขเป็นการเดา

คำถามหลักที่ตอบไม่ได้:

> **วันที่ไม่มีรายได้ เกิดจากอะไร?**

สาเหตุที่เป็นไปได้มี 4 อย่าง และแต่ละอย่างแก้คนละวิธีสิ้นเชิง

| สาเหตุ | วิธีแก้ |
|---|---|
| ไม่ได้เปิดร้าน | แก้ที่ความสม่ำเสมอของตัวเอง |
| เปิดแล้วแต่ไม่มีคนทัก | ต้องขยายช่องทางหาลูกค้า |
| มีคนทักแต่ปิดการขายไม่ได้ | ต้องแก้ราคา / ของ / วิธีตอบ |
| ขายได้แต่ลืมจด | ปัญหาคุณภาพข้อมูล ไม่ใช่ปัญหาธุรกิจ |

ถ้าเก็บแค่ "รายการขาย" จะแยก 4 อย่างนี้ไม่ออกเลย เพราะทั้งหมดหน้าตาเหมือนกันคือ *ไม่มีแถว*
ระบบนี้จึงมีตาราง `day_log` ที่บันทึก**ทุกวัน** ไม่ใช่เฉพาะวันที่ขายได้

## ปัญหาที่ยากที่สุด: ต้นทุนไม่ใช่ตัวเลขที่จ่ายไป

ไอเทมในเกมซื้อด้วย **Token** ไม่ใช่เงินบาท และ Token ซื้อมาจากพ่อค้าใน**อัตราที่ไม่คงที่**

```
ต้นทุนจริง (บาท) = Token ของไอเทม ÷ เรทที่ได้ Token มา
```

ของแบบเดียวกันราคา 192 Token อาจมีต้นทุนจริงต่างกันเกือบเท่าตัว ขึ้นกับว่า Token มาจากไหน:

| แหล่งที่มา | เรท | ทุนของ 192 Token |
|---|---|---|
| ซื้อ Token จากพ่อค้าในกลุ่ม | 10 – 11.1 | 17.3 – 19.2 บาท |
| **รับ "เหมา" มาย่อยขายเอง** | **17 – 25** | **7.7 – 11.3 บาท** |

"เหมา" คือมีคนโพสต์ขายของยกชุดในราคาเดียว โดยที่ RAP รวมของทั้งชุดสูงกว่ามูลค่าที่ควรได้จากเรทปกติ
ตัวอย่างโพสต์จริงในกลุ่ม: ขายเหมา **130 บาท** ได้ของ 7 ชิ้น เฉพาะ 5 ชิ้นที่มองเห็น
RAP รวมกันแล้ว **2,297** → เท่ากับเรท **17.7 Token/บาท ดีกว่าเรทพ่อค้า 1.6 เท่า**

### แต่สองทางนี้ไม่ได้เทียบกันตรงๆ ได้

| | ซื้อ Token | รับเหมา |
|---|---|---|
| จ่ายเงินแล้วได้อะไร | **Token ทันที** | **ไอเทม** ไม่ใช่ Token |
| เอาไปใช้ได้เลยมั้ย | ได้ | **ไม่ได้ — ต้องตั้งบูธขายก่อน Token ถึงเข้าตัว** |
| รู้เรทเมื่อไหร่ | ตอนจ่ายเงิน | ตอนย่อยขายหมดแล้ว |
| ความเสี่ยง | ไม่มี | ชิ้นที่ขายไม่ออก = เงินจม |

### ค่าธรรมเนียมบูธ 1%

ตอนตั้งขายไอเทมที่บูธ เกมหักค่าธรรมเนียมไป วัดจากในเกมจริง 3 จุด:

| ตั้งขาย | ได้จริง | สูตร `floor(ราคา × 0.99)` |
|---|---|---|
| 17 | 16 | 16 ✓ |
| 20 | 19 | 19 ✓ |
| 40,000 | 39,600 | 39,600 ✓ |

ทั้งสามเคสตรงกับ **1% ปัดลง** พอดี → ตั้งขายเท่า RAP เป๊ะจะได้กลับมาไม่ครบเสมอ
ต้องตั้งสูงกว่า RAP ราว 1.1% ขึ้นไป (RAP 670 → ตั้ง 677 ถึงจะได้ 670 คืน)

**การตั้งราคาที่บูธไม่ได้ทำเพื่อเอากำไร** — ตั้งแค่พอไม่ขาดทุนจาก RAP
เพราะกำไรถูกล็อกไว้ตั้งแต่ตอนรับเหมาถูกแล้ว บูธเป็นแค่ทางแปลงไอเทมเป็น Token

### เรทมี 3 ชั้น

| | คิดยังไง | ตัวอย่างล็อต 130฿ RAP 2,297 |
|---|---|---|
| `rate_on_paper` | RAP ÷ บาท | **17.67** ← เลขที่เห็นตอนกดซื้อ |
| `rate_expected` | RAP × 0.99 ÷ บาท | **17.49** ← หักค่าบูธแล้ว |
| `rate_actual` | Token ที่ได้จริง ÷ บาท | **13.85** ถ้าขายออกแค่ 79% |

ผลต่างของ 3 ชั้นนี้คือราคาของความเสี่ยงที่จ่ายไปเพื่อแลกกับเรทที่ดูดีกว่า
และเป็นคำถามที่ตอบไม่ได้เลยถ้าไม่เก็บข้อมูล

### ต้นทุน 2 ชั้น

เพราะของเหมาทำให้ต้นทุนต่อชิ้นเป็นแค่การประมาณ ระบบจึงแยกตัวเลขเป็น 2 ชั้น:

| | คิดยังไง | ใช้ทำอะไร |
|---|---|---|
| **กำไรเงินสดจริง** | เงินลูกค้าโอนเข้า − เงินที่จ่ายซื้อของ | ต้องตรงกับยอดกรุงไทยเป๊ะ ใช้ตอนปิดเดือน |
| **กำไรรายออเดอร์** | Σ (ราคาขาย − Token ÷ เรท) | ใช้วิเคราะห์ว่าของแบบไหนคุ้ม |

ผลต่างของสองชั้นนี้ = **มูลค่าที่ยังค้างอยู่ในของที่ซื้อมาแล้วขายไม่ออก** ไม่ใช่การจดผิด
บอทจะรายงานส่วนต่างนี้ให้ตอนปิดเดือน เพื่อไม่ให้เข้าใจผิดว่าตัวเลขเพี้ยน

## ปัญหาที่สอง: ไอเทมมีเป็นหมื่นชิ้น แทบไม่ซ้ำกันเลย

คำถาม *"ไอเทมไหนขายดีที่สุด"* ตอบไม่ได้ เพราะ `GROUP BY ชื่อไอเทม` จะได้กลุ่มละ 1 แถว

ทางออกคือ**ไม่ใช้ชื่อไอเทมเป็นมิติในการวิเคราะห์** แต่ใช้คุณสมบัติที่ซ้ำได้แทน:

- **ช่วงราคา Token** (`token_band`) ← มิติที่สำคัญที่สุด
- ประเภท (ดาบ / ระเบิด / ท่าทาง)
- กลุ่ม Facebook ที่ลูกค้ามา
- แหล่งที่มาของ Token

ชื่อไอเทมยังเก็บอยู่ในคอลัมน์ `note` เผื่ออยากย้อนดู แต่ไม่ถูกใช้ aggregate

## สมมติฐานที่ตั้งไว้ และผลจากข้อมูลจริง

การตั้งราคาของร้านนี้ไม่ได้ใช้สูตร ใช้ความเคยชิน — และผลคือ**อัตราส่วนกำไรกลับหัว**

| ทุน (Token) | ทุน (บาท) | ขาย | กำไร | ขายได้กี่เท่า | กำไร/Token |
|---|---|---|---|---|---|
| 100 | 9 | 80 | **71** | 8.8x | **0.71** |
| 500 | 45 | 80 | 35 | 1.8x | 0.07 |
| 2,200 | 200 | 240 | 40 | 1.2x | 0.018 |

*(เรท 11 Token/บาท · ตัวเลขจากราคาที่ขายจริงเป็นประจำ)*

**สมมติฐาน: ของถูกทำกำไรได้มากกว่าของแพง ทั้งต่อครั้งและต่อ Token**
เพราะร้านตั้งราคาเป็นทอดๆ (เช่นเหมา 55 หรือ 80 บาท) ในขณะที่ทุนต่างกันหลายเท่า
ส่วนของแพงจะต่อราคาลงมาเหลือ 1.2–1.5 เท่าของทุน ทำให้กำไรต่อครั้งพอๆ กับของถูก
แต่ใช้เวลาหาของนานกว่ามาก

ถ้าข้อมูลยืนยันว่าจริง แปลว่าควร**เลิกไล่ล่าของแพง** — นี่คือการตัดสินใจที่โปรเจกต์นี้ตั้งใจจะตอบ
→ ดู [`analysis/queries.sql`](analysis/queries.sql) ข้อ Q2

### ผลจริง (456 ออเดอร์ 15 ก.ย. – 17 พ.ย. 2026)

| ช่วง Token | ออเดอร์ | กำไรเฉลี่ย/ออเดอร์ (บาท) | กำไร/Token |
|---|---|---|---|
| ต่ำกว่า 100 | 30 | 64 | 1.30 |
| 100–299 | 83 | 79 | 0.44 |
| 300–599 | 143 | 107 | 0.25 |
| 600–1,499 | 116 | 147 | 0.16 |
| 1,500 ขึ้นไป | 84 | 434 | 0.09 |

**ถูกครึ่งเดียว และครึ่งที่ผิดคือครึ่งที่สำคัญ** ของถูกได้กำไร*ต่อ Token* มากกว่าจริง แต่ของแพงได้**กำไรต่อออเดอร์มากกว่า 6.8 เท่า** (434 vs 64 บาท)
Token ไม่ใช่ทรัพยากรจำกัด กำไรต่อ Token จึงเป็นตัวชี้วัดที่ผิด ตัวที่ได้เงินจริงคือกำไรต่อออเดอร์
**ตัดสินใจ: ขายของแพงต่อ** ถ้าเลิกตามสมมติฐานเดิม จะตัดแหล่งกำไรก้อนใหญ่ที่สุดทิ้ง

## สถาปัตยกรรม

```
Telegram (พิมพ์บรรทัดเดียว)
        │
        ▼
   src/parser.py     แปลง "55 192 10.5 ดาบ a" เป็นข้อมูลมีโครงสร้าง
        │
        ▼
   src/db.py  ──────► PostgreSQL (Supabase) ตอนใช้งานจริง · SQLite ตอนทดสอบในเครื่อง
        │                 └─ VIEW v_sale / v_day คำนวณต้นทุน-กำไรที่เดียว
        ▼
   analysis/queries.sql → ตอบคำถามธุรกิจด้วย SQL
```

**ทำไมแยก 3 ไฟล์:** `parser.py` กับ `db.py` ไม่รู้จัก Telegram เลย
ถ้าจะเพิ่ม LINE ทีหลัง เขียนแค่ตัวรับข้อความใหม่ ส่วนที่เหลือใช้ซ้ำได้ทั้งหมด

**ทำไมกำไรเป็น VIEW ไม่ใช่คอลัมน์:** ถ้าเก็บ `profit` เป็นค่าจริง แล้ววันหลังแก้ `token_rate`
ย้อนหลัง ตัวเลขจะไม่ตรงกัน — คำนวณสดเสมอปลอดภัยกว่า

## วิธีติดตั้ง

```bash
pip install -r requirements.txt
```

1. เปิด Telegram หา **@BotFather** → `/newbot` → ตั้งชื่อ → ได้ token มา
2. ก๊อป `.env.example` เป็น `.env` แล้ววาง token ลงช่อง `BOT_TOKEN`
3. ดับเบิลคลิก `run.bat`
4. ทักบอทใน Telegram 1 ครั้ง → เลข `CHAT_ID` จะขึ้นในหน้าต่างดำ → เอาไปใส่ `.env`
5. ปิดแล้วเปิด `run.bat` ใหม่ — เสร็จ

## วิธีใช้

พิมพ์บรรทัดเดียวจบ ส่งทีละหลายบรรทัดก็ได้ (จดรวดเดียวก่อนนอน)

**ตอนได้ของเข้าร้าน** บันทึกครั้งเดียว แล้วบอทจะจำเรทไว้ใช้กับทุกรายการขายหลังจากนั้น

```
/ซื้อ 700 63          ซื้อ Token 63฿ ได้ 700 Token → เรท 11.1
/เหมา 2297 130 7      รับเหมา 130฿ ได้ 7 ชิ้น RAP รวม 2,297 → เรทคาดหวัง 17.5
/ตั้ง 670             ของ RAP 670 ตั้งขายที่บูธเท่าไหร่ → ตั้ง 677 ได้ 670
/ย่อย 1800            ย่อยขายได้จริง 1,800 Token → เรทจริง 13.9
```

**ตอนขาย** พิมพ์แค่ 2 ตัวเลข

```
55 192
150 565 คละ b x3 +170
80 340 10.5 ดาบ a          ใส่เรทเฉพาะบรรทัดก็ได้
เมื่อวาน 55 192 #Dual Hacker Scythe
```

| ส่วน | ความหมาย |
|---|---|
| ตัวเลขที่ 1 | ราคาที่ขายได้จริง (บาท) |
| ตัวเลขที่ 2 | **Token ที่กดจ่ายจากบูธจริง** — ไม่ใช่ Your Value (RAP) ซึ่งต่ำกว่า 2-4% |
| ตัวเลขอื่น | เรท Token — ไม่ใส่ = ใช้เรทจาก `/ซื้อ` หรือ `/เหมา` ล่าสุด |
| **`2297/130`** | **เรทแบบเศษส่วน — จ่าย 130฿ ได้ RAP รวม 2,297 บอทหารให้เอง** |
| `ดาบ` `ระเบิด` `ท่า` `คละ` | ประเภทไอเทม |
| `a` `b` | กลุ่ม Facebook ที่ลูกค้ามา |
| `x3` | จำนวนชิ้นในออเดอร์ |
| `+170` | ราคาที่ตั้งไว้ก่อนลด |
| `เหมา` | รับของยกชุดมาย่อยขาย (เรท ≥ 13 ติดป้ายให้อัตโนมัติ) |
| `เมื่อวาน` `d15` | ลงย้อนหลัง |
| `#...` | หมายเหตุ เช่น ชื่อไอเทม |

**คำสั่ง:** `/ซื้อ` `/เหมา` `/ตั้ง` `/ย่อย` `/today` `/yesterday` `/week` `/month` `/band` `/rate 2297 130` `/inq 5` `/close` `/undo` `/help`

### บอทจะทักกลับมาเอง

- **ทุกเที่ยงคืน** — สรุปยอดของวันที่เพิ่งจบ เทียบเป้ารายวัน (`TARGET_DAY` ใน `.env`)
  เลือกเที่ยงคืนเพราะช่วงขายดีที่สุดคือ **1 ทุ่ม–4 ทุ่ม** (เด็กเลิกเรียน) สรุปก่อนหน้านั้นจะได้ตัวเลขไม่ครบ
  ถ้าวันนั้นไม่มียอดเลย จะถามว่าเพราะอะไร พร้อมปุ่มให้กด 4 ปุ่ม
- **ขายดึกหลังเที่ยงคืน** — พิมพ์ `เมื่อวาน` นำหน้า แล้วยอดจะไปลงวันที่ถูกต้อง
- **ทุกวันจันทร์** — สรุปสัปดาห์ที่เพิ่งจบ เทียบเป้ารายสัปดาห์ (`TARGET_WEEK` ใน `.env`)
- **ถ้าบอทไม่ได้เปิดไปหลายวัน** — จะไล่ถามสาเหตุของวันที่ตกหล่นย้อนหลัง 7 วันให้
- **ทุกวันที่ 1** — ขั้นตอนโอนเงิน และ**ตรวจว่ายอดที่จดตรงกับยอดในบัญชีมั้ย**
  (ยอดกรุงไทยควรเท่ากับ เงินค้าง 1,000 + กำไรที่จดไว้ ถ้าต่างเกิน 100 บาท แปลว่ามีที่ผิด)
